## 0. 작업 규칙 (저장소 `AGENTS.md`에서 온 제약)

- 별도 브랜치에서 작업하고 Pull Request로 리뷰받는다. `main` 직접 푸시, 강제 푸시, 배포는 승인 없이 하지 않는다.
- 운영 D1 데이터 변경, 마이그레이션 재실행, 키 등록, 유료 AI 호출은 팀 합의 후에만 한다.
- 기존 마이그레이션 파일은 고치지 않고 **번호를 올린 새 파일**로 추가한다.
- 질문이 한 번이라도 있었던 게임 기록은 지우지 않는다. 허용된 삭제는 "7일 지난, 질문·요청·제출이 없는 빈 게임"뿐이다.
- 현재 운영은 **테스트 모드(고정 응답)**. 실제 AI 호출은 Workers 런타임에서 아직 검증되지 않았다.
- API 응답 형태, 비공개 정보(역할 A~D, 사실 태그, 해금 상태는 제출 전 브라우저로 보내지 않음), 멱등성(요청 ID, 지문, 게임 버전)은 제거하지 않는다.

## 1. 지적된 두 가지 문제

| 번호 | 문제 | 원인 |
|---|---|---|
| P1 | 병렬 실행으로 쓸모없는 답변이 만들어진다 | 분류와 답변을 동시에 시작해서, 분류 결과로 새 해금이 생기면 해금 전 상태로 만든 답변이 틀린 것이 되어 처음부터 다시 만든다 (시간·비용 2배) |
| P2 | 빠른 모델이 질문만 보고 해금한다 | 질문 문장이 취지에 맞기만 하면 해금되고, 정답과의 의미상 근접도나 근거 유무를 보지 않는다. 첨부로 푸는 해금은 어떤 AI도 의미를 판단하지 않는다 |

## 2. 대원칙 [확정]

- **해금 여부를 결정하는 것은 빠른 모델(LLM)이다.** 코드는 의미를 판단할 수 없고, 결정에 따라 **기록하고 메인 모델용 프롬프트를 조립**한다.
- 코드가 하는 일: 점수 합산, 해금선 비교, 상태 저장, 질문 수 차감, 형식 확인(고를 수 있는 사실인지), 이미 풀린 사실 유지.
- 해금 정확도는 **빠른 모델의 품질과 판단 기준(프롬프트)에 달려 있다.** 판정 이유 한 줄을 남겨 추적 가능하게 한다.

## 3. 처리 순서 [확정] (P1 해결)

```
① 빠른 모델: 질문 수 세기 + 질문별 기준 판정 (구조화된 형식)
② 코드: 반려 여부 → 절대 기준 확인 → 점수 합산 → 해금선 비교
③ 코드: 해금 사실 저장 + 질문 수만큼 차감 + 메인 모델 프롬프트 조립
④ 메인 모델: 1회만 호출 (말투를 입혀 답변)
⑤ 빠른 모델: 답변 검증 (누설·규칙 위반)
```

- 빠른 모델의 판정을 **먼저 기다린다.** 메인 모델은 정확한 상태를 받아 한 번만 호출된다.
- 판정에서 반려/되묻기가 나오면 메인 모델은 부르지 않는다.
- 대가: 모든 턴에 빠른 모델 한 번 분량의 대기가 붙는다. 실제 모델 연결 후 시간을 측정해 확인한다.
- 용어: 답변 전 판정은 **"해금 판정"**, 답변 후 확인은 **"답변 검증"**으로 구분한다.

## 4. 해금 판정 기준 [확정] (P2 해결)

빠른 모델은 결론("해금")을 쓰지 않고 **기준별 값만** 정해진 형식으로 돌려준다. 이유를 먼저 쓴 뒤 값을 채우게 한다. 해금 대상은 그 NPC의 **아직 잠긴 사실 중에서만** 고르게 제한한다. 질문·첨부·기록 안의 지시는 따르지 않는다.

### 4.1 절대 기준 (하나라도 "아니오"면 해금 불가)

| 번호 | 기준 | 비고 |
|---|---|---|
| G1 | 앞 단계 사실이 이미 풀렸는가 | 기록 대조라 가장 안정적 |
| G2 | 첨부가 있으면 질문이 첨부 내용과 연결되는가 (첨부 없으면 해당 없음) | 카드 던지기 방지. 지금은 첨부만 하면 통과되는 빈틈 |
| G3 | 질문이 구체적인 대상(장소·물건·행동·사람 중 하나 이상)을 짚었는가 | 사실과 맞는지는 보지 않고 **구체성만** 본다 (맞는 정도는 S1) |

(기존 "한 질문에 여러 의도" 기준은 절대 기준에서 **제외**하고 5장의 차감 방식으로 처리한다.)

### 4.2 점수 기준 (절대 기준 통과 후 합산)

| 번호 | 기준 | 점수 |
|---|---|---|
| S1 | 풀려는 사실과 일치하는 정도 | 0 / 1 / 2 |
| S2 | 얻은 정보에서 이끌어낸 질문인가 (근거성) | 0 / 1 / 2 |
| S3 | 이전 대화에서 이어진 질문인가 | 0 / 1 |
| S4 | 유도형 질문 (질문에 답을 담아 동의를 구함) | 0 / -1 |

#### 4.2.1 점수 부여 기준 [확정, 2026-11-25]

빠른 모델은 아래 기준으로 값을 정한다. 근거로 인정하는 정보는 **이번 질문의 첨부 + 이 NPC와의 대화 기록**뿐이다 (찾고 안 낸 단서는 서버가 모르므로 인정하지 않음).

| 기준 | 점수 | 부여 조건 |
|---|---|---|
| S1 사실 일치 | 2 | 질문이 풀려는 사실의 핵심 요소(누가·무엇을·어디서·언제 중 그 사실이 담은 것)를 **2개 이상** 짚음 |
| | 1 | 핵심 요소를 **1개** 짚음 |
| | 0 | 구체적이지만 이 사실과 무관함 (다른 사실이나 딴 주제) |
| S2 근거성 | 2 | 질문의 핵심 내용이 첨부한 단서·증언 또는 이 NPC가 이미 한 말에서 **직접 이끌어낼 수 있고** 그 내용과 맞물림 |
| | 1 | 일부만 뒷받침되거나, 근거 정보는 있으나 질문에 그 이상의 구체 내용이 섞임 |
| | 0 | 플레이어가 가진 정보로는 알 수 없는 구체 내용을 갑자기 언급 |
| S3 이어짐 | 1 | 이 NPC와의 직전 두 턴의 주제를 이어 묻거나 직전 답변 내용을 받아서 물음 |
| | 0 | 그 외 |
| S4 유도형 | -1 | **근거로 뒷받침되지 않는 내용을 질문 안에 단정으로 넣고** 동의를 구함 (예: 증거 없이 "당신이 꽂았죠?") |
| | 0 | 그 외. 첨부한 증거에서 나온 결론을 묻는 것은 유도형이 아님 |

- **G3와 S1의 역할 분리**: G3는 "구체적인 대상을 짚었나"만, S1은 "그 대상이 이 사실과 얼마나 맞나"를 본다. 그래서 G3를 통과해도 S1이 0일 수 있고, 이때는 근접 구간에도 들지 못한다.

- **"같은 주제를 말만 바꿔 찔러봄" 기준은 뺐다** (여러 턴을 거슬러 의도를 추측해야 해서 모델이 불안정).
- 원칙: **이번 요청에 넣어 준 재료만 보고 답할 수 있는 기준만** 남긴다.
- 점수 범위: -1 ~ 5. 작은 모델이 안정적이도록 칸을 좁게(0/1/2) 둔다.

### 4.3 해금선과 결과 [확정, 2026-11-25]

해금선은 **사실마다 시나리오 데이터로 지정**한다 (점수 매기는 방법은 모두 같고 문턱만 다름).

| 사실의 성격 | 해금선 |
|---|---|
| 일반 | 3점 |
| 중요 | 4점 |
| 핵심 자백 | **S1·S2 모두 2점(만점)** (총점 4 이상은 자동 충족) |

- **해금**: 절대 기준 통과 + 해금선 이상
- **근접**: 절대 기준 통과 + 해금선 미만 + S1이 1점 이상 → 해금하지 않고 NPC 반응(표정)만 변경
- **무관**: 그 외 (변화 없음)
- **3단계로 확정한다.** 사실 분류 (범인 D 줄거리 기준 초안, 시나리오 담당 검수 필요):

| 분류 | 사실 |
|---|---|
| 일반 (3점) | a_receipt, b_source, b_record, c_why, c_roulette, d_cable_excuse |
| 중요 (4점) | a_testimony, b_typing, c_cable, d_receiver |
| 핵심 (S1·S2 만점) | d_delete, d_motive |

- 분류 기준: 범인을 직접 가리키거나 범행 사실의 일부를 밝힐수록 높게, 용의자 개인의 사소한 숨김은 낮게.
- 숫자는 시작값이다. **정확/근접/애매/엉뚱한 질문 평가 세트**로 돌려 오해금과 놓침을 재면서 조정한다. 오해금(풀리면 안 되는데 풀림)을 놓침보다 더 해롭게 본다.

### 4.4 점수 조합 예시 (일반 3 / 중요 4 / 핵심 S1·S2 만점)

| (S1,S2,S3,S4) | 합계 | 일반 | 중요 | 핵심 |
|---|---|---|---|---|
| (2,2,0,0) | 4 | 해금 | 해금 | 해금 |
| (2,1,1,0) | 4 | 해금 | 해금 | 근접 |
| (2,0,0,0) 근거 없이 정확히 맞힘 | 2 | 근접 | 근접 | 근접 |
| (2,2,0,-1) 유도형 | 3 | 해금 | 근접 | 근접 |

## 5. 여러 질문 처리와 차감 [확정]

- 한 번에 여러 질문을 **허용**한다. 빠른 모델이 "따로 대답해야 하는 별개 질문 수"를 세고, 그 수만큼 **남은 질문을 차감**한다.
- **한 번에 최대 3개.** 4개 이상이면 반려.
- 질문 수 세기 기준: 풀어 쓴 한 질문은 1로 센다, 애매하면 **적게** 센다.
- **남은 횟수보다 많이 물으면 반려** (차감 없음, 써 둔 내용 유지).
- 해금 판정은 **질문 하나하나에 대해** 따로 한다 (정확한 질문에 엉뚱한 질문을 섞는 오판 방지). 빠른 모델 출력은 "질문 목록 + 질문별 판정"이 된다.
- 메인 모델은 각 질문에 짧게 답한다. 캐릭터별 답변 길이 규칙은 질문 수만큼 허용하도록 조정해야 한다.
- 화면: 이미 있는 "남은 질문" 표시에 **차감 개수 한 줄**("질문 N회 사용")을 대사창에 추가하고, 입력창 안내문 "한 번에 하나씩 물어보자"를 바꾼다. 화면 담당과 맞춘다.
- [확정] "알 수 없는 질문"은 NPC가 속마음으로 되묻고 차감하지 않는다. 단 차감 없는 응답(되묻기·반려)이 **연속 3번**이면 다음 응답은 1회 차감한다 (무한 반복 방지, 7.5 참조).

## 6. 속마음 연출 [확정]

원칙: **게임 세계 안의 탐정 속마음 말투로 말한다.** 시스템 용어("횟수 초과", "오류", "제한")는 쓰지 않는다. 문장은 **미리 쓴 고정 문장**에서 코드가 고르고, AI가 생성하지 않는다. 같은 문장 반복을 피하려고 상황별 **3~4개 변형**을 번갈아 쓴다. 말투는 기존 화면처럼 괄호 없이 "~하자 / ~다".

### 6.1 반려 문구

| 상황 | 문구 (예) |
|---|---|
| 남은 질문보다 많이 물음 | "남은 시간이 얼마 없다. 두 가지만 추려서 물어보자." (개수는 상황에 맞게) |
| 마지막 1개인데 여러 개 | "이제 정말 한 가지밖에 못 묻는다. 가장 중요한 걸 고르자." |
| 한 번에 4개 이상 | "한꺼번에 다 묻기엔 상대가 부담스러워 한다. 세 가지까지만 해 보자." |

### 6.2 그 밖의 시스템 안내도 같은 목소리로 [제안, 팀 확인]

| 기존 문구 | 속마음 버전 (예) |
|---|---|
| 답변을 만들지 못했습니다… | "말이 잘 안 이어진다. 질문을 조금 바꿔서 다시 물어보자. 질문은 아직 쓰지 않았다." |
| 무엇을 묻는지 조금 더 구체적으로… | "내가 무슨 말을 하려던 거지? 묻고 싶은 걸 좀 더 또렷하게 해 보자." |
| 서버 오류입니다 | "잠깐 정신이 멍했다. 한 번 더 해 보자." |

- 주의: 기술 오류의 원인은 화면에 안 보이게 **로그로 남긴다.** "질문이 차감되지 않았다"는 정보는 속마음에 꼭 포함한다.

### 6.3 반복 실패 시 힌트 속마음

- **같은 기준이 3번 연속 낮게 나오면** 그 기준 하나만 속마음으로 알려준다. (너무 쉬우면 재미없으므로 바로 알려주지 않음)
- 보여준 뒤 그 기준의 횟수는 0으로 되돌리고, 그 기준에서 **좋은 점수를 받으면** 횟수도 초기화한다.
- 여러 기준이 동시에 3번이면 하나만(절대 기준 실패 → 점수가 가장 낮은 기준 순).
- **절대 금지**: 단서 이름, 사실 내용, 증거의 위치, 특정 인물 지목, "방향이 맞다/가깝다" 같은 정답 확인, 점수 숫자 노출. **허용**: 어느 부분이 부족했는지와 바꿔 볼 행동의 종류, NPC의 태도 관찰.
- 원인별 문구(예): 근거 부족 "아직 확실한 근거가 없다. 증거를 좀 더 찾아보고 다시 물어보자." / 유도형 "내가 답을 정해 놓고 묻고 있었다. 상대가 경계하는 것 같다. 유도하지 말고 상대 입으로 말하게 해 보자." / 핵심 못 짚음 "너무 두루뭉술하게 물었다. 언제, 어디서, 무엇을 했는지 콕 집어서 물어보자." / 첨부 불일치 "내민 증거와 질문이 따로 논다. 보여 준 것과 이어지게 물어보자."
- 게임 상태에 "기준별 연속 낮음 횟수" 기록이 추가로 필요하다.
- [확정, 2026-11-25] **연속 3번** (설정값으로 두고 실제 플레이로 조정). **게임 단위**로 센다. 한 메시지는 1회로 세며, 메시지 안의 질문 중 하나라도 해당 기준이 낮으면 그 메시지는 "낮음"이다. **"낮음"의 정의**: G1·G2·G3 실패, S1=0, S2=0, S4=-1 (S3는 보너스라 세지 않음). 근접 반응은 **NPC 표정 변화로만** 표현하고, 속마음에서는 방향을 확인해 주지 않는다.

## 7. 남용·비용 방어 [확정/미정 혼합]

### 7.1 현재 코드의 빈틈 (확인함)

- 새 게임 생성만 IP당 분당 10번 제한이 있고, **질문 API에는 속도 제한이 없다.**
- **되묻기·반려는 질문 횟수를 차감하지 않으면서 AI를 부른다** (되묻기 1회, 반려 최대 4회). 새 설계의 "초과 반려(차감 없음)"도 같은 위험을 이어받는다 → 차감 없는 호출에도 내부 상한이 필요하다.
- 전체 비용 상한이 없다. 키 등록 **전에** 막아야 한다.

### 7.2 핵심 원칙

- 클라이언트가 가진 값(쿠키, 입력값)으로 하는 제한은 제한이 아니다.
- 방당 호출 상한만으로는 방을 여러 개 만드는 경우를 막지 못한다. **확실한 상한은 하루 전체 예산과 AI 제공자 한도뿐**이다.
- 로그인 없이도 비용 폭탄은 막을 수 있다. 로그인이 필요한 이유는 "공격자가 예산을 소진시켜 정상 사용자가 못 쓰는 것"을 막기 위해서다.

### 7.3 확정된 방어 구성

| 항목 | 내용 | 상태 |
|---|---|---|
| 접속 허용 | **학원 공인 IP 허용 목록** (+ 팀원 예외). 외부는 VPN을 써도 접속 불가 | [확정] 학원 IP는 **고정으로 가정**. 단 현재 주소가 workers.dev라 방화벽 규칙을 쓸 수 있는지 **확인 필요** → 안 되면 서버 입구에서 접속 IP를 목록과 비교 |
| IP당 동시 존재 방 수 | **30개** (한 사람당 2개 기준 약 15명) | [확정] |
| 분당 방 생성 제한 | **두지 않음** (허용 IP 목록이 전제. 외부 공개 시 느슨한 제한 재도입) | [확정] |
| 한 사람당 방 수 | **2개** (진행 중인 방 기준, 쿠키로 방어. 조작은 가정하지 않음) | [확정] |
| 새 게임 생성 조건 | 현재 게임을 **클리어하거나 종료한 뒤**에만 | [확정] |
| 방 확인 방식 | 쿠키의 방 번호로 서버 기록 조회. 쿠키에는 번호만 있고 남은 질문·해금 상태는 서버 기록에 있음 | [확정] |
| 사람 식별 | 쿠키의 **플레이어 번호**(한 번 발급)로 서버 기록에서 방 수를 셈 | [확정] |
| 30개가 찼을 때 | 속마음 안내 (예: "지금은 수사에 나선 사람이 많다. 잠시 뒤에 다시 와 보자.") | [확정] |

### 7.4 세션 만료·차단 (삭제하지 않음) [확정]

- 방 기록은 **지우지 않고, 접속만 차단**한다. 로그가 필요할 수 있고 팀 규칙(기록 삭제 제한)에도 맞는다.
- 상태: **진행 중 / 종료 / 차단(만료) / 차단(관리자)**. 종료·차단 방은 방 개수에서 제외한다.
- 휴면 기준 [확정]: **마지막 요청 후 15분 무응답이면 만료** (빈 방·질문한 방 구분 없음). 수용한 절충: 빈 방도 15분 유지되어 한 사람이 자리를 오래 차지할 수 있으나, 사람당 2개 제한과 학원 내 신뢰로 감수한다. 만료 판단은 하루 한 번의 정리 작업이 아니라 **요청이 올 때와 새 방을 만들 때 그 자리에서** 한다. 요청마다 마지막 활동 시각을 갱신한다.
- 차단된 방은 질문·제출·새 게임 요청 모두에서 같은 확인을 거쳐 거절하고, 속마음 안내를 보여준다 (예: "시간이 많이 지났다. 새로 수사를 시작하자.").
- 기록할 것: 차단 시각, 차단 사유(휴면 만료/관리자 차단), 마지막 활동 시각, 플레이어 번호.
- 탭 종료 신호는 **보조**로만 쓴다 (새로고침과 구분 불가, 전달 보장 없음). 쓴다면 몇 분의 유예를 둔다. 상태 정리의 기준은 신호가 아니라 **시간**이다.
- [확정] 만료된 방은 **새로 시작만** 가능 (이어하기 없음). [미정] 이름 입력(자기 신고) 도입 여부, 관리자 조회 화면(처음엔 데이터베이스 직접 조회).

### 7.5 비용 상한 장치 [확정: 최소 구성 / 나머지 보류]

| 순서 | 장치 |
|---|---|
| 1 [확정] | AI 제공자의 **월 사용 한도 설정 한 번** (코드 없음). 허용 IP 안쪽의 실수·버그·장난에 대비한 최후 방어선. 키 등록 권한자와 합의 |
| 2 [확정] | **차감 없는 응답(반려·되묻기)이 연속 3번이면 다음 응답은 1회 차감** (차감 없는 호출의 무한 반복 방지) |
| 3 [보류] | 하루 전체 예산 기능 (도달 시 테스트 모드 전환). 허용 IP로 외부가 막혀 있어 개발하지 않음. 외부 공개 시 재검토 |

| 6 [선택] | 게임별 호출 횟수 기록 (이상 발견용) |

- 기존 새 게임 생성 제한(IP당 분당 10번)은 학원 동시 시작 때 걸리므로 **조정 또는 제거**해야 한다.
- 외부 공개 시에는 새 방 생성에 봇 확인(Turnstile)과 느슨한 생성 제한, 필요하면 초대 코드나 로그인을 검토한다.

## 11. 프롬프트 캐싱과 호출 예산 [확정, 2026-11-25]

**호출 예산 (테스트)**
- 자동 테스트는 실제 AI를 부르지 않는다. 실제 호출 검증은 총 60회 안쪽으로 계획표를 세워 쓰고, 호출 수 카운터와 상한 초과 시 중단 장치를 둔다. 반복·재시도 폭주 금지, 같은 검증은 결과를 재사용한다.
- 호출마다 모델·지연·입력/출력/캐시 토큰을 기록해 최종 보고에 실제 호출 수와 비용 규모를 적는다.

**프롬프트 캐싱을 적극 활용하는 흐름**
1. 앞부분(공통 규칙, 사건 개요, 역할 배경, 캐릭터, 사실 전체 목록)은 게임·NPC 동안 바이트 단위로 같게 고정하고, 현재 상태·대화 기록·첨부·질문은 맨 뒤에 둔다.
2. 해금 판정은 사실 전체 목록을 항상 같은 순서로 두고 해금 가능/선행 미충족/이미 풀림 표시는 뒤쪽 가변 부분에 둔다. 출력 스키마는 NPC 단위로 고정하고 유효성은 코드가 확인한다.
3. 같은 모델을 쓰는 해금 판정과 답변 검증은 공통 앞부분을 같은 순서로 맞추고 작업별 지시문을 뒤에 붙여 캐시를 공유한다.
4. 대화 기록은 앞에서부터 추가만 한다.
5. 캐시 최소 길이 확인, 캐시 묶음 키·보관 시간 옵션은 쓰는 모델이 지원하면 사용한다.
6. 캐시 토큰으로 적중률을 측정해 보고한다.

### 12.1 해금 판정

| # | 결정 | 이유 |
|---|---|---|
| 1 | 예전 조건 문법(`unlock`)과 의도 목록(`ask:`)은 **없앴다**. `has:` → 앞 단계(`after`, 코드가 기록 대조), `cite:`·`clue:` → 필요 근거(`needs`, 판정 재료 + S2 상한). 사실마다 근거 안내(`basis`) 문장도 준다. 테스트 모드는 핵심 요소 키워드(`keywords`)와 필요 근거로 흉내 낸다 | 결정 1. 원칙 "해금 결정은 LLM, 코드는 실행·기록·형식 확인" |
| 2 | G1(앞 단계)은 모델이 아니라 **코드가** 판정한다. 모델에는 사실 전체를 주고, 가변 부분 [사실 상태]에 "처음부터 말하는 사실 / 이미 털어놓음 / 해금 가능 / 앞 단계 미충족(먼저 풀려야 할 것)"과 필요 근거 확인 여부를 적는다. 모델이 고른 사실이 앞 단계 미충족이면 G1 실패 | 결정 2. 기록 대조는 기계적인 일이다 |
| 3 | 형식 검사: target 은 구조화 출력 enum(**그 NPC의 전체 사실 ID** + `none`, NPC 단위로 고정)으로 제한하고, 처음부터 아는 사실·이미 풀린 사실을 골라도 코드가 무시한다 | 설계 4장 "아직 잠긴 사실 중에서만". 스키마를 질문마다 바꾸지 않아야 캐시가 유지된다(12.9) |
| 4 | 질문마다 사실 하나만 판정한다. 앞 단계·필요 근거는 **메시지를 받기 전 상태**로 한 번만 계산한다(연쇄 해금 없음). 같은 사실을 두 질문이 겨눠도 한 번만 풀린다 | 결정 3 |
| 5 | 일반·중요는 합계만 본다(결정 5). 다만 **S1=0 은 "겨냥 사실 없음"으로 정리**한다(형식 확인) | **결정 5와의 차이**: 프롬프트 정의상 S1=0 은 "무관하거나 target 이 none" 이다. target 을 적고 S1=0 을 준 출력은 자기모순이라, 그대로 두면 (0,2,1,0)=3 으로 무관한 일반 사실이 풀린다(처음 구현 때 테스트로 발견). 해금선·합산 규칙은 그대로이고 모순된 출력만 "none"으로 고친다. 팀이 원하면 `scoreQuestion` 한 줄로 되돌릴 수 있다 |
| 6 | 핵심 사실은 **S1=2, S2=2, 합계 4 이상**. 그래서 유도형 (2,2,0,-1)=3 은 근접 | 4.4 예시 표와 맞춤 |
| 7 | **근거성(S2)의 형식 확인**: (가) 첨부도 이 NPC와의 대화 기록도 없으면 S2=0, (나) 모델이 근거 인용(basis)을 "없음"으로 적으면 S2=0, (다) 겨냥 사실의 필요 근거가 이번 첨부·지난 첨부에서 확인되지 않으면 S2 최대 1(결정 1). 근거 인용 칸은 S2 바로 앞에 둔다 | (가)(나)는 실제 모델이 근거 없는 질문에 S2=2를 줘 오해금 3건이 난 것을 막는다. 4.2.1의 정의를 기계적으로 적용한 것이라 의미 판단이 아니다 |

| 9 | 근접은 메인 모델 프롬프트에 아무것도 넣지 않고, 답의 표정이 '기본'이면 '당황'으로만 바꾼다 | "표정만 변경", 내용 누설 위험 없음 |

### 12.4 방 관리와 접속 제한

| # | 결정 |
|---|---|
| 1 | 방 상태: `active`(진행 중) / `ended`(종료: 제출했거나 새 게임으로 넘어감) / `blocked_expired`(차단: 15분 무응답) / `blocked_admin`(차단: 관리자). 차단 사유 `idle`/`admin`, 차단 시각, 마지막 활동 시각, 플레이어 번호를 기록한다(마이그레이션 0004). 지우지 않는다 |
| 2 | "진행 중 방" = 상태 active **이고** 마지막 활동이 15분 이내. 그래서 휴면이지만 아직 표시 안 된 방도 방 수에서 빠진다. 진행 중 방만 담는 부분 인덱스 2개로 세는 행 수를 줄였다 |
| 3 | 사람당 2개·전체 30개 제한은 **새 방을 넣는 INSERT 한 문장 안에서** 센다(동시에 눌러도 넘지 않음). 새 게임은 같은 트랜잭션에서 지금 방을 종료로 바꾸되, **새 방이 실제로 만들어졌을 때만** 바꾼다. 지금 방은 셀 때 빼므로 2개를 가진 사람도 새 게임은 할 수 있다 |
| 4 | 차단된 방에서 새 게임을 하면 그 방은 차단 상태 그대로 둔다(종료로 덮어쓰지 않음) |
| 5 | 휴면 만료는 요청이 올 때(세션·질문·제출·조사) 그 자리에서 판단해 기록한다. 매일 정리 작업은 보조로 오래된 진행 중 방을 만료로 표시한다(지우지 않음). 기존 "7일 지난 빈 게임 삭제"는 승인된 예외라 그대로 둔다 |
| 6 | 마지막 활동 시각은 질문·제출의 저장 문장에 함께 넣어 **추가 쓰기가 없다**. 조회만 하는 요청(세션, 조사)은 60초가 지났을 때만 쓴다. 그래서 만료 판단에 최대 1분 오차가 있다 |
| 7 | 차단된 방: 질문·제출·조사는 410 + 속마음 + `closed`(`expired`/`admin`). 세션 조회는 200으로 기록을 보여 주되 선택 필드 `closed: { reason, message }` 를 붙이고, 화면은 "새 수사 시작" 버튼만 보여 준다 |
| 8 | 방이 가득 차면 둘 다 **429** + 속마음 + 선택 필드 `code`(`player_rooms_full` / `rooms_full`). 게임 쿠키는 바꾸지 않고, 플레이어 번호가 없던 사람에게는 이때도 `player` 쿠키를 발급한다. **결정 10과의 차이**: 다른 오류(예: 다른 사이트의 폼 전송 415)에는 붙이지 않는다. SameSite=Strict 라 그런 요청에는 기존 쿠키가 실려 오지 않아, 붙이면 진짜 플레이어 번호를 새 번호로 덮어쓰게 된다(기존 보호 테스트가 잡음). 첫 접속에서 방을 못 만들면 화면은 그 속마음을 "탐정" 안내로 보여 준다 |
| 9 | 플레이어 번호 쿠키 `player`(HttpOnly, SameSite=Strict, 1년)는 처음 접속할 때 한 번 발급한다. 마이그레이션 전 기록은 플레이어 번호가 없어 사람당 집계에서 빠진다. 기존 기록은 제출한 게임을 종료로, 마지막 활동을 만든 시각으로 채웠다 |
| 10 | 서비스 전체 상한은 상수 30, 환경 변수 `MAX_ACTIVE_ROOMS` 로 바꿀 수 있다 |
| 11 | 접속 IP 허용 목록은 Worker 입구에서 `cf-connecting-ip` 를 `ALLOWED_IPS`(쉼표 구분, 정확한 IP 또는 IPv4 CIDR, IPv6는 정확 일치만)와 비교한다. 비어 있으면 제한 없음. API는 JSON 403, 화면은 짧은 안내 페이지. 실제 IP는 저장소에 쓰지 않는다 |

### 12.5 로컬 Worker에서 실제 키 쓰기 (확인함)

- 로컬 개발 런타임은 Worker 설정에 **선언된 비밀 값만** `.dev.vars` 에서 채운다. 선언이 없으면 키를 넣어도 테스트 모드로 돈다.
- 운영 배포에 영향을 주지 않으려고 `cloudflare.config.ts` 는 `GOTBONG_LOCAL_AI=1` 일 때만 `OPENAI_API_KEY`·`GEMINI_API_KEY` 를 비밀 값으로 선언한다. `npm run dev:ai` 가 이 값을 켜고 개발 서버를 띄운다.
- 확인: `npm run dev:ai` → `/api/session` 의 `mode` 가 `openai`, 질문 2개 메시지가 Workers 런타임에서 한 번에 답하고 2회 차감(6.4초).

### 12.9 캐시 친화 호출 흐름 (요구 B)

| 항목 | 구현 | 이유 |
|---|---|---|
| 배치 | 메시지 = [system: 고정 앞부분] [system: 작업 지시] [user: 가변]. 가변 부분은 대화 기록(한 턴 한 줄, 오래된 것부터, 끝에만 추가) → 상태 → 첨부 → 질문 순 | OpenAI 자동 캐시는 앞부분이 같은 요청끼리 재사용한다. 바뀌는 것은 뒤로 |
| 빠른 모델 공통 앞부분 | 해금 판정과 답변 검증이 같은 `fastPrefix`(자료 머리말, 사건 개요, 공개 단서 카드, 대상의 처지·모르는 것·하지 않는 말·잡담 정보, **사실 전체 목록**: 내용·숨김 설명·핵심 요소·필요 근거·근거 안내·앞 단계·철회 조건)를 쓴다. 상태·시각·무작위 값은 넣지 않는다 | 게임·NPC 동안 바이트 단위로 같고, 판정 캐시를 검증이 이어 쓸 수 있게 |
| 공통 출력 스키마 | 두 작업이 `{ result: 판정 갈래 \| 검증 갈래 }` 하나의 스키마(NPC 단위 고정, 사실 ID는 전체 목록)를 쓴다. 코드가 갈래(task)와 ID 유효성을 확인 | OpenAI 문서상 출력 형식(스키마)도 캐시 앞부분을 정하는 설정이라, 작업마다 스키마가 다르면 앞부분이 갈라진다 |
| 초안(메인 모델) | system(규칙·캐릭터·역할)은 원래대로 고정, user 는 대화 기록부터 | 같은 NPC 반복 질문에서 재사용 |
| 묶음 키 | `prompt_cache_key` = 게임 ID와 역할로 만든 짧은 해시(게임 ID 자체는 보내지 않음). `OPENAI_CACHE_KEY=off` 로 끌 수 있다 | 문서 권장: 같은 앞부분 요청을 같은 키로. 키당 분당 약 15회 권장 → 한 게임·한 NPC는 그보다 훨씬 적다 |
| 보관 시간 | `OPENAI_CACHE_RETENTION`(in_memory·24h)을 지정했을 때만 보낸다. 기본은 보내지 않음 | 문서상 24h 지원 목록에 gpt-4.1 은 있고 gpt-4.1-mini 는 없다. 메모리 캐시는 보통 비활성 5~10분(최대 1시간) 유지라 수업 중 연속 질문에는 충분하다. 지원하지 않는 모델에 보내 호출이 실패할 위험을 피했다 |
| 최소 길이 | 빠른 모델 공통 앞부분은 역할에 따라 약 2,400~4,000자(한국어), 실측 캐시 1,920 토큰 | 문서상 1,024 토큰 이상이어야 캐시된다 |

실측 (`docs/game/eval/cache-probe-*.md`, 같은 게임·NPC에 질문 2번, 6회 호출):

| 호출 | 입력 | 캐시 | 비율 |
|---|---|---|---|
| 1 판정(첫 호출) | 3,179 | 0 | 0% |
| 2 초안(첫 호출) | 2,750 | 0 | 0% |
| 3 검증(판정 직후) | 2,369 | 0 | 0% |
| 4 판정(두 번째) | 3,254 | 1,920 | 59% |
| 5 초안(두 번째) | 2,891 | 1,920 | 66% |
| 6 검증(두 번째) | 2,527 | 1,920 | 76% |

- 같은 작업의 두 번째 호출부터 캐시가 맞았다(전체 입력 16,970 중 5,760, 34%. 첫 호출을 빼면 8,672 중 5,760, 66%).
- **판정 → 검증 공유는 확인하지 못했다**: 판정 1.6초 뒤의 첫 검증은 캐시 0. 두 번째 판정·검증이 같은 1,920 토큰을 맞힌 것은 공통 앞부분 크기와 일치하지만, 첫 검증이 만든 캐시를 쓴 것인지 판정의 것을 쓴 것인지는 이 실측으로 구분할 수 없다. 캐시가 만들어지는 데 시간이 걸리거나, 작업 지시가 다른 지점에서 캐시 경계가 잡히지 않았을 수 있다.

### 12.10 실제 호출 예산 (요구 A)

- 자동 테스트(`npm test`)는 Fixture·가짜 모델만 쓴다. 두 테스트 파일은 실제 AI 주소로 나가는 요청을 막아 실패시킨다.
- 실제 호출 스크립트(`eval`, `judge-probe`, `cache-probe`)는 모두 `lib/ai/budget.mjs` 장부를 거친다. 장부(`docs/game/eval/ai-calls.jsonl`)에 호출마다 시각·스크립트·작업·모델·지연·입력/출력/캐시 토큰을 남기고, 누적이 `AI_CALL_BUDGET`(기본 60)에 닿으면 호출 전에 멈춘다. 스크립트마다 `--max-calls` 상한도 있다. 모델 재시도는 2회 이하.
- 장부 도입 전 호출은 요약 한 줄(53회, 상한 기준으로 잡음)로 넣었다. 로컬 Worker(`npm run dev:ai`)를 거친 호출은 Worker 런타임에서 파일을 쓸 수 없어 장부에 자동으로 남지 않는다(수동 요약에 포함).

| 검증 | 계획 | 실제 |
|---|---|---|
| 해금 판정 평가 1차(판정 17 + 전체 처리 2) | 25 | 25 |
| 판정 프롬프트 보정 후 평가 | 17 | 17 |
| 경계 사례(첨부 불일치) 재확인 | 6 | 6 |
| 로컬 Worker 실제 키 확인 | 5 | 약 4~5 (인코딩이 깨진 요청 1회 포함) |
| 캐시 적중 확인(요구 B) | 6~7 | 6 |
| **합계** | **60 이하** | **59 (장부 기준, 로컬 Worker 상한으로 셈)** |

요구 A·B는 1~4번 검증이 끝난 뒤 전달돼서 예산을 미리 나눠 잡지 못했고, 남은 7회 안에서 캐시 확인만 했다. 토큰 규모: 캐시 확인 6회 합계 입력 16,970·출력 600 토큰. 질문 하나(판정·초안·검증)는 입력 약 8천 토큰이다.

### 12.11 필수 근거(G4)와 단서 발견 서버 기록 (2026-11-26, 브랜치 `feat/evidence-gate-clue-record`)

참고: 팀원 제안 "유령 키보드 v2" 서버·시나리오 패치와 AI 프롬프트 패치(ZIP). 그대로 적용하지 않고 목적만 받아 다시 구현했다.

| # | 문제 | 결정 | 이유 |
|---|---|---|---|
| 1 | 단서를 찾지 않고 내용을 맞혀 말하면 자백이 풀림 (일반: S1 2 + S2 0 + S3 1 = 3, 중요: 2+1+1 = 4, 실측 1건) | **절대 조건 G4(필수 근거) 신설.** 사실에 `needs` 가 있으면, 그 근거를 이 NPC에게 실제로 내밀었는지(이번 첨부 + 지난 첨부, `state.evidence`) 코드가 확인하고 없으면 점수와 관계없이 해금하지 않는다. `needs` 가 없는 사실은 해당 없음 | "증거를 갖췄나"는 정도가 아니라 예/아니오라서 점수(S2 상한)가 아니라 절대 조건이 맞다. 결정 1(필요 근거 = S2 최대 1)을 바꾼다. S2 상한 보정은 그대로 둔다 |
| 2 | 참고 패치는 근거 부족을 상태 `blocked`(G1 실패)로 처리 → 힌트가 "순서대로 묻자"로 나감, 필드 `requiredEvidence` 가 `needs` 와 따로 있어 `d_delete` 에서 서로 어긋남 | G1(순서)과 G4(근거)를 나누고, 새 필드 없이 `needs` 하나만 쓴다. `d_delete` 는 기존대로 "B 타이핑 증언 또는 빌드 기록 + 휴지통" | 같은 정보는 한 곳에. 근거 부족이면 G4 힌트(증거를 내밀라)가 나간다 (`HINT_ORDER` = G1, G4, G2, G3, S4, S1, S2) |
| 3 | G4 범위 | `needs` 가 있는 모든 사실 (D 4단계뿐 아니라 a_testimony, b_source, b_typing, c_cable 포함) | 지금 `needs` 를 따라가면 순환이 없고 모두 처음 사실이나 찾을 수 있는 단서에서 출발한다(막다른 길 없음). 어느 사실에 붙일지 따로 정할 필요가 없다 |
| 4 | 찾지 않은 단서도 첨부 가능 (서버는 존재만 확인) | 모든 현장 클릭을 서버가 판정하고(`lib/game/data/spots.mjs` 한 표 + 사람 모니터), 찾은 단서를 `games.clues_found`(마이그레이션 `0006`)에 기록. 질문 API는 기록된 단서만 첨부 허용(400 + 속마음 `clueNotFound`, 차감 없음) | 판단에 필요한 사실은 서버가 소유한다 |
| 5 | 참고 패치는 발견 기록을 `state` 에 넣고 revision 을 올림 → 질문을 기다리는 사이 조사하면 질문 저장이 409, 또는 덮어써서 기록 손실 | 별도 열에 `json_insert` 한 문장으로 추가만 하고 revision 은 바꾸지 않는다 | 질문 저장(state 덮어쓰기)과 다른 곳을 써서 충돌·손실이 없다. 같은 곳을 여러 번 눌러도 한 번만 남는다 |
| 6 | 배포 순간 진행 중인 방: 브라우저에만 있던 단서 | 화면이 세션을 불러올 때 서버에 없는 단서를 찾은 자리로 다시 조사해 등록. 서버 기록은 이 브라우저에 없어도 수첩에 보인다 | 기존 플레이어가 단서를 잃지 않게 |
| 7 | 모순 해결 진행도 | 따로 저장하지 않고 해금 기록에서 계산(`progressOf`, `case.mjs contradictions` 4개). **최종 제출 결과(`result.progress`)에만** 싣는다 | G4 이후 해금 = 순서 + 필요 근거 + 검증 통과. 범인 쪽 사실이라 제출 전에 보내면 범인을 알려 주는 셈(4장 비공개 정보 계약) |
