# AI 추리게임 설계 문서 (최종본)

작성일: 2026-11-17
개정: 기존 회의 기획서 대비 누락 사항 1~4 반영

## 1. 목표

플레이어 4명이 한 방에 들어와 학원 교실에서 벌어진 일상 사건을 조사한다. 현장을 살펴 증거를 모으고, AI 용의자 4명을 각자 취조해, 누가 어떤 경위로 일을 벌였는지를 가장 적은 질문으로 맞힌 사람이 이긴다. 운영 비용 0원을 목표로 한다.

## 2. 콘셉트

- **배경**: 팀원들이 실제로 다니는 학원과 교실.
- **분위기**: 살인 같은 무거운 사건이 아니라 가볍고 웃긴 일상 미스터리.
- **사건 원인**: 고의뿐 아니라 실수, 우연, 자연 고장도 정답이 될 수 있다. 그래서 최종 추리는 "누가"와 "어떤 경위로"를 함께 고르고, "누가"에는 "아무도 아님"이 선택지로 들어간다.
- **반전**: 가장 의심스러운 사람(마지막으로 물건을 쓴 사람, 흔적이 남은 사람)이 범인이 아니도록 시나리오를 짠다.
- **용의자**: 개발팀 구성원 4명을 모델로 한다. 본인이 동의한 경우에만 실제 이름과 말투를 쓴다.

## 3. 게임 규칙

| 항목 | 규칙 |
|---|---|
| 인원 | 방당 최대 4명. 방장이 시작을 누르면 시작한다. 1명만 있어도 시작할 수 있다(혼자 테스트용). |
| 용의자 | AI 4명. 시나리오 파일에 정의된다. |
| 제한 시간 | 시작 시점부터 20분. 종료 시각은 서버가 정한다. |
| 현장 조사 | 교실 화면의 사물을 눌러 단서를 찾는다. 횟수 제한이 없고 질문 수에 포함되지 않는다. 찾은 단서는 증거 수첩에 쌓인다. |
| 일반 심문 | 1인당 질문 20개. 용의자 4명에게 자유롭게 나눠 쓴다. 질문 하나는 200자 이내. |
| 증거 제시 | 질문할 때 증거 수첩의 증거 하나를 함께 내밀 수 있다. 질문 1개로 센다. |
| 복합 질문 | 메시지 하나는 내용과 관계없이 질문 1개로 센다. 한 메시지에 질문이 여러 개면 용의자는 첫 질문에만 답하고 하나씩 물어 달라고 말한다. |
| 집중 심문 | 선택 사항. 최종 추리 전에 가장 의심되는 용의자 1명을 골라 2분 동안 최대 5개를 더 묻는다. 1인 1회. 20개 한도와는 별도이지만 순위 계산에는 합산한다. 전체 시간이 먼저 끝나면 함께 끝난다. |
| 정보 공개 | 문답과 증거 수첩은 본인만 본다. 다른 플레이어는 닉네임, 사용한 질문 수, 제출 여부만 본다. |
| 최종 추리 | "누가", "어떤 경위로", "결정적 증거"를 선택지에서 고르고, 추리 이유를 한두 문장으로 적어 제출한다. 1인 1회이며 제출하면 그 플레이어의 조사는 끝난다. |
| 정답 | "누가"와 "어떤 경위로"를 둘 다 맞혀야 정답이다. |
| 승자 | 정답자 중 총 질문 수(일반 + 집중)가 가장 적은 사람. 같으면 결정적 증거를 맞힌 사람, 그래도 같으면 먼저 제출한 사람. |
| 정답자 없음 | 승자 없음으로 끝내고 보고서만 공개한다. |
| 시간 초과 | 20분이 지나면 미제출자는 오답 처리한다. |
| 종료 조건 | 전원이 제출했거나 20분이 지났을 때. |
| 보고서 | 종료 후 방의 모든 플레이어에게 공개한다. |

추리 이유는 채점하지 않고 보고서에 싣는다. 자유 서술을 AI로 채점하면 결과가 판마다 달라지고 비용이 들기 때문이다.

질문 20개, 집중 심문 2분·5개, 제한 시간 20분은 설정 파일 한 곳(`lib/game/config.ts`)에 두고, 플레이 테스트 결과에 따라 조정한다.

## 4. 첫 번째 사건: 사라진 도시락

용의자 이름은 팀원 동의를 받은 뒤 실제 이름으로 바꾼다. 아래에서는 A~D로 적는다.

### 4.1 사건 개요 (플레이어에게 공개)

매니저님이 아침 9시에 탕비실 냉장고에 넣어 둔 파란 뚜껑 도시락(제육볶음)이 12시 50분에 사라졌다. 점심시간에 교실에 있던 네 사람이 용의자다.

### 4.2 진상 (보고서에서 공개)

A가 자기 도시락인 줄 알고 실수로 먹었다. A는 오늘 똑같은 파란 뚜껑 통에 도시락을 싸 왔다고 생각했지만, 실제로는 집 식탁에 두고 왔다. 12시 10분에 냉장고의 파란 통을 꺼내 전자레인지에 데워 먹었고, 소동이 난 뒤에야 자기 것이 아니었음을 깨닫고 겁이 나서 통을 씻어 싱크대에 엎어 두었다.

- **정답**: 누가 = A, 경위 = 자기 것인 줄 알고 실수로 먹음, 결정적 증거 = A의 가방
- **반전**: 냉장고를 마지막으로 열었고 입가에 빨간 소스가 묻은 B는 범인이 아니다.

### 4.3 시간표

| 시각 | A (실수로 먹음) | B (미끼) | C (목격자) | D (외출) |
|---|---|---|---|---|
| 11:50 | 자리에서 공부 | 자리에서 공부 | 자리에서 공부 | 냉장고를 열어 물을 꺼냄. 파란 통이 하나뿐인 것을 봄 |
| 12:00 | 자리 | 편의점으로 나감 | 컴퓨터로 과제 시작 | 식당으로 나감 |
| 12:10 | 냉장고에서 파란 통을 꺼내 전자레인지에 데움 | 편의점 | 탕비실 쪽에서 제육 냄새를 맡고 A가 나오는 것을 봄 | 식당 |
| 12:25 | 자리에서 식사 | 편의점에서 떡볶이를 사서 먹음 | 과제 | 식당 |
| 12:30 | 식사를 마침 | 교실로 돌아옴 | 과제 제출 | 식당 |
| 12:40 | 자리 | 냉장고를 열어 음료를 꺼냄. 파란 통이 없는 것을 봄 | 자리 | 식당 |
| 12:50 | 매니저님이 도시락이 없다고 알림. A가 통을 씻어 싱크대에 둠 | 자리 | 자리 | 교실로 돌아옴 |

### 4.4 용의자가 숨기는 것

| 용의자 | 처음 하는 말 | 숨기는 것 | 털어놓는 조건 |
|---|---|---|---|
| A | "내 도시락을 아침에 냉장고에 넣어 뒀고, 점심에 그걸 먹었다." | 자기 도시락을 집에 두고 왔다는 것 | 'A의 가방' 증거를 내밀면 실수를 인정한다 |
| B | "점심은 안 먹었다. 12시 40분에 음료만 꺼냈다." | 다이어트를 선언해 놓고 떡볶이를 먹은 것 | '쓰레기통' 증거를 내밀면 떡볶이를 인정한다 |
| C | "과제 하느라 누가 탕비실에 갔는지 못 봤다." | 친구 A가 탕비실에서 나오는 것을 본 것 | '전자레인지' 증거를 내밀면 A를 봤다고 말한다 |
| D | 숨기는 것 없음. "11시 50분에 파란 통은 하나뿐이었다." | 없음 | 해당 없음 |

한 명만 취조해서는 풀 수 없다. A의 "내 통을 넣어 뒀다"는 말은 D의 "통은 하나뿐이었다"와 어긋나고, B의 "12시 40분에는 통이 없었다"는 말이 사라진 시각을 좁혀 준다.

### 4.5 현장 단서

| 단서 | 누르는 곳 | 내용 |
|---|---|---|
| 냉장고 | 탕비실 냉장고 | 파란 통이 없다. 음료와 물만 있다. |
| 전자레인지 | 탕비실 전자레인지 | 안쪽에 제육 양념이 튀어 있고 아직 미지근하다. |
| 싱크대 | 탕비실 싱크대 | 씻어 엎어 둔 파란 통. 바닥에 매니저님 이름 스티커가 붙어 있다. |
| 쓰레기통 | 교실 쓰레기통 | 떡볶이 용기와 12시 25분 편의점 영수증. |
| B의 입가 | 용의자 B | 입가에 빨간 소스가 묻어 있다. |
| C의 컴퓨터 | C 자리의 컴퓨터 | 12시 30분 과제 제출 기록. |
| A의 가방 | A 자리의 가방 | 도시락이 없다. 열린 틈으로 휴대폰 알림이 보인다. "도시락 식탁에 두고 갔더라." |

### 4.6 경위 선택지

1. 배고파서 일부러 훔쳐 먹었다
2. 자기 것인 줄 알고 실수로 먹었다 (정답)
3. 장난으로 숨겼다
4. 상한 줄 알고 버렸다
5. 아무도 가져가지 않았다. 다른 곳에 놓여 있었다

### 4.7 후속 사건 후보

컴퓨터가 꺼진 사건, 문손잡이 고장, 소금물 사건. 자연 고장이나 우연이 정답인 사건은 이쪽에서 다룬다.

## 5. 기술 구성

- **웹/서버**: Next.js (App Router, TypeScript), Vercel 무료 요금제에 배포
- **DB**: Supabase Postgres 무료 요금제. 서버만 서비스 키로 접근하고, 브라우저는 DB에 직접 접근하지 않는다.
- **AI**: Google Gemini API 무료 요금제. 모델 이름은 환경 변수 `GEMINI_MODEL`로 지정한다.
- **방 상태 동기화**: 브라우저가 2초마다 방 상태 API를 조회한다. 4명 규모에서는 충분하고, 문답이 비공개여야 하므로 브라우저가 DB를 직접 구독하지 않는 편이 안전하다.
- **환경 변수**: `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `GEMINI_API_KEY`, `GEMINI_MODEL`. 모두 서버 전용이다.

현장 조사는 미리 써 둔 단서를 보여 주는 것이라 AI를 부르지 않는다. 한 판의 AI 호출은 최대 100번(1인당 일반 20 + 집중 5)이다.

## 6. 구성 요소

각 요소는 하나의 역할만 맡고, 아래 인터페이스로만 서로를 부른다.

### 6.1 시나리오 (`scenarios/`)

시나리오 1편은 TypeScript 파일 하나와 이미지 폴더 하나다.

```ts
type Scenario = {
  id: string;
  title: string;
  intro: string;                 // 사건 개요
  scene: { background: string; hotspots: Hotspot[] };
  clues: Clue[];
  suspects: Suspect[];           // 정확히 4명
  causes: { id: string; label: string }[];   // 경위 선택지
  solution: { suspectId: string | null; causeId: string; keyClueId: string };
  truth: string;                 // 보고서에 실리는 진상
};

type Hotspot = { clueId: string; x: number; y: number; w: number; h: number };  // 배경 대비 %
type Clue = { id: string; name: string; text: string; image?: string };

type Emotion = "neutral" | "flustered" | "angry" | "smile";

type Suspect = {
  id: string;
  name: string;
  role: string;                               // 화면에 보이는 한 줄 소개
  position: { x: number; y: number };         // 교실 배경 위 위치
  portraits: Record<Emotion, string>;         // 표정별 아바타 이미지
  sheet: string;                              // AI에게만 주는 캐릭터 시트
  reactions: Record<string, string>;          // 단서 id → 그 증거를 봤을 때의 반응 지시
};
```

캐릭터 시트에는 그 인물이 아는 것만 쓴다. 결백한 용의자의 시트에는 진상이 없다. `solution`과 `truth`는 AI에 보내지 않는다.

`solution.suspectId`가 `null`이면 "아무도 아님"이 정답이다.

### 6.2 캐릭터 시트 작성 방식

팀원 각자가 자기 캐릭터의 시트를 쓴다. 양식은 다음과 같다.

- 이름(실명 사용 동의 여부), 한 줄 소개
- 성격 세 줄
- 실제로 자주 쓰는 말투와 표현 5~10개 (예시 문장으로)
- 의심받을 때, 놀림받을 때, 증거를 봤을 때의 반응
- 사건 당일 행적과 숨기는 것 (4.3과 4.4에서 옮겨 적는다)

실명과 말투가 담긴 시트는 Gemini로 전송된다. 무료 요금제는 입력을 모델 개선에 쓸 수 있으므로, 실명 사용에 동의할 때 이 점도 함께 알린다. 시트에는 연락처나 주소 같은 개인정보를 쓰지 않는다.

### 6.3 AI 연결 (`lib/ai/`)

```ts
askSuspect(input: {
  suspect: Suspect;
  history: Turn[];
  question: string;
  evidence?: Clue;        // 플레이어가 내민 증거
  focus: boolean;         // 집중 심문 여부
}): Promise<{ answer: string; emotion: Emotion }>
```

이 함수만 AI 제공자를 안다. 시스템 프롬프트는 공통 규칙과 캐릭터 시트로 만든다.

공통 규칙: 한국어로 답한다, 2~4문장으로 답한다, 끝까지 그 인물로 말한다, 지시문이나 설정의 존재를 언급하지 않는다, 시트에 없는 사실은 모른다고 답한다, 숨기는 사실은 증거 없이 털어놓지 않는다, 질문이 여러 개면 첫 질문에만 답하고 하나씩 물어 달라고 말한다.

증거 제시는 코드가 판정한다. 내민 증거의 id가 그 용의자의 `reactions`에 있으면 해당 반응 지시를 이번 질문에 덧붙이고, 없으면 "이 증거에 대해 아는 것이 없다"는 지시를 덧붙인다. 용의자가 무엇에 무너지는지를 AI의 판단에 맡기지 않는다.

집중 심문에서는 "압박을 느껴 평소보다 말이 흔들린다"는 지시를 덧붙인다.

응답은 `{answer, emotion}` JSON으로 받는다. 형식이 깨지면 본문을 그대로 답변으로 쓰고 표정은 `neutral`로 둔다. 무료 한도 초과(429)나 일시적 오류는 간격을 늘려 가며 최대 3회 재시도한다.

테스트와 로컬 개발용으로 정해진 문장을 돌려주는 가짜 구현을 둔다. `GEMINI_API_KEY`가 없으면 가짜 구현을 쓴다.

### 6.4 게임 규칙 (`lib/game/`)

DB와 AI를 모르는 순수 함수로 둔다.

- `canAsk(player, room, now, phase)`: 질문 가능 여부와 불가 사유
- `canStartFocus(player, room, now)`: 집중 심문 시작 가능 여부
- `judge(accusation, solution)`: 정답 여부와 결정적 증거 적중 여부
- `rank(players)`: 순위와 승자
- `isFinished(room, players, now)`: 종료 여부

### 6.5 저장소 (`lib/db/`)

Supabase 호출을 감싼다. 모든 테이블은 RLS로 익명 접근을 막는다.

| 테이블 | 열 |
|---|---|
| `rooms` | `id`, `code`(6자), `scenario_id`, `status`(waiting / playing / finished), `started_at`, `ends_at` |
| `players` | `id`, `room_id`, `nickname`, `token`, `is_host`, `questions_used`, `focus_suspect`, `focus_started_at`, `focus_used`, `asking_since`, `submitted_at`, `accused_suspect`, `accused_cause`, `accused_clue`, `reason`, `is_correct`, `clue_correct` |
| `player_clues` | `player_id`, `clue_id`, `found_at` |
| `messages` | `id`, `room_id`, `player_id`, `suspect_id`, `phase`(general / focus), `clue_id`, `question`, `answer`, `emotion`, `created_at` |

### 6.6 API (`app/api/`)

방 생성과 입장을 뺀 모든 요청은 플레이어 토큰을 헤더로 보낸다. 토큰은 입장할 때 발급해 브라우저 localStorage에 저장한다. 로그인은 없다.

| API | 동작 |
|---|---|
| `POST /api/rooms` | 방을 만들고 만든 사람을 방장으로 입장시킨다. `{닉네임}` → `{방 코드, 토큰}` |
| `POST /api/rooms/{code}/join` | 대기 중이고 4명 미만일 때 입장한다. `{닉네임}` → `{토큰}` |
| `POST /api/rooms/{code}/start` | 방장만 가능. 상태를 playing으로 바꾸고 `ends_at`을 정한다. |
| `GET /api/rooms/{code}/state` | 방 상태, 남은 시간, 플레이어별 진행 상황, 시나리오 공개 정보(개요, 배경, 누를 수 있는 위치, 용의자 이름·소개·아바타, 선택지), 본인의 문답과 증거 수첩을 준다. 종료 조건을 여기서 확인한다. |
| `POST /api/rooms/{code}/investigate` | `{단서}` → 단서 내용. 증거 수첩에 기록한다. |
| `POST /api/rooms/{code}/ask` | `{용의자, 질문, 증거?}` → `{답변, 표정, 남은 질문 수}` |
| `POST /api/rooms/{code}/focus` | `{용의자}`를 받아 집중 심문을 시작한다. 이후 `ask`는 그 용의자에게만, 2분 동안, 5개까지 가능하다. |
| `POST /api/rooms/{code}/accuse` | `{누가, 경위, 결정적 증거, 이유}`를 받아 판정 결과를 저장한다. 결정적 증거는 본인이 찾은 단서 중에서만 고를 수 있다. 정답 여부는 종료 전까지 알려 주지 않는다. |
| `GET /api/rooms/{code}/report` | 방이 finished일 때만 보고서 데이터를 준다. |

단서 내용은 `investigate`를 호출해야만 내려간다. `state`에는 누를 수 있는 위치만 들어 있어, 브라우저 개발자 도구로 단서를 미리 볼 수 없다.

### 6.7 화면 (`app/`)

| 화면 | 내용 |
|---|---|
| 로비 | 닉네임 입력, 방 만들기, 코드로 입장 |
| 대기실 | 방 코드와 공유 링크, 입장한 사람 목록, 방장의 시작 버튼 |
| 교실 | 2D 교실 배경 위에 용의자 4명과 조사할 사물이 놓여 있다. 사물을 누르면 단서가 뜨고, 용의자를 누르면 심문 창이 열린다. 상단에 남은 질문 수와 시간, 다른 플레이어 진행 상황, 증거 수첩과 최종 추리 버튼. |

| 보고서 | 순위와 승자, 사건의 진상, 플레이어별 추리와 이유, 플레이어별 찾은 단서, 플레이어별·용의자별 전체 문답(증거 제시와 집중 심문 표시 포함). 브라우저 인쇄로 PDF 저장이 되도록 인쇄용 스타일을 둔다. |

폰 화면 폭에서 먼저 맞춘다.

### 6.8 그림 자산

| 자산 | 수량 | 준비 |
|---|---|---|
| 교실 배경(탕비실 포함) | 1장 | 팀 |
| 용의자 아바타 | 4명 × 표정 4종(기본, 당황, 화남, 웃음) = 16장 | 팀 |
| 단서 그림 | 7장 (선택) | 팀 |

아바타는 미모지처럼 본인을 닮은 스타일로 만든다. 애플 미모지로 만든 이미지를 그대로 공개 배포하는 것은 이용 조건에 걸릴 수 있으므로, 팀 내부 플레이를 넘어 공개할 때는 직접 그린 그림으로 바꾼다.

그림이 준비되기 전에는 단색 도형과 이모지로 된 임시 그림으로 개발한다. 파일만 바꿔 끼우면 되도록 경로를 시나리오 파일에서 지정한다.

## 7. 질문 한 번의 흐름

1. 브라우저가 `ask`를 호출한다.
2. 서버가 토큰으로 플레이어를 찾고 `canAsk`를 확인한다(진행 중, 시간 남음, 미제출, 한도 미만, 처리 중인 질문 없음, 집중 심문이면 그 용의자이고 2분 이내).
3. 증거를 내밀었다면 본인이 찾은 단서인지 확인한다.
4. `asking_since`를 조건부 UPDATE로 기록한다. 동시에 두 번 눌러도 한 번만 통과한다.
5. 그 플레이어와 그 용의자의 문답 기록을 읽어 `askSuspect`를 호출한다.
6. 성공하면 문답과 표정을 저장하고 질문 수를 1 늘린 뒤 `asking_since`를 지운다.
7. 실패하면 `asking_since`만 지우고 오류를 돌려준다. 질문 수는 차감하지 않는다.

## 8. 오류 처리

| 상황 | 처리 |
|---|---|
| AI 호출 실패 | 질문을 차감하지 않고 "다시 시도해 주세요"를 보여 준다. |
| 시간 종료 직후 도착한 질문 | 거절한다. 종료 전에 시작된 호출의 답변은 저장한다. |
| 집중 심문 중 AI 응답 지연 | 2분은 서버 시각 기준이며 늘려 주지 않는다. |
| 새로고침·재접속 | localStorage의 토큰으로 같은 플레이어로 복귀한다. |
| 진행 중인 방에 새로 입장 | 거절한다. |
| 중간에 나간 플레이어 | 별도 처리 없음. 시간이 지나면 오답 처리된다. |
| 응답이 끊겨 `asking_since`가 남음 | 60초가 지나면 무시한다. |

## 9. 테스트

- `lib/game/`의 순수 함수는 단위 테스트로 검증한다: 질문 한도, 집중 심문 조건, 시간 초과, 판정, 순위와 동점 처리, 정답자 없음, "아무도 아님"이 정답인 경우.
- 증거 제시 판정을 단위 테스트로 검증한다: 맞는 증거, 무관한 증거, 찾지 않은 증거.
- API는 가짜 AI와 테스트용 저장소로 한 판 전체 흐름을 검증한다: 생성, 입장, 시작, 조사, 질문, 증거 제시, 집중 심문, 제출, 보고서.
- 프롬프트는 자동 테스트하지 않는다. 실제 Gemini로 직접 플레이하며 용의자가 설정을 지키는지 확인하고 시트를 다듬는다.
